# F1 — edgeml sighting sidecar wired into the Go edge

**Question.** Does the Go edge store one item per *object* instead of one per *frame* when it talks to the
edgeml pipeline (detect → track → `SightingAggregator`) through the sidecar, and what does it cost per frame?

**Setup.** `cmd/edge` (`./bin/edge -dedup <mode> -scenario … -period 200ms`, i.e. 5 fps, no shore reachable so
everything stays queued) against `python -m edgeml.sidecar --detector ~/models/D/yolo11n-640/model.onnx --embed
~/models/D/mobileclip-s1` (YOLO11n FP32 ONNX on ONNX Runtime CPU, ByteTrack/centroid via boxmot, `SightingAggregator`
with `relink_gap_s=20, min_update_interval_s=10`, MobileCLIP-S1 zero-shot subtype on the key crop), 4 threads
(`taskset -c 0-3`, 8-vCPU VM). Clips: two **dev** sequences of `ghost_fleet_5fps` per `edgeml/configs/splits.yaml`
(`Spotted_A_Submarine` is a *test* clip there, so it was not used): `Submarine_surfacing` (372 frames, 1280×720,
object visible from frame 173) and `Cruise_ship_Mediterranean_sunset_off_Italy` (153 frames, 1080×1920, ship visible
throughout). Both clips streamed back-to-back as sources `cam-sub` / `cam-cruise`, 525 frames total, one sidecar
restart per mode. The same sidecar is called in all three modes (only the edge-side policy differs).

Second run (follow-up PR, same clips/models/flags; `naive`/`hash` re-measured at 525 items / 85.5 MB / 49.8 and
48.9 ms/frame): object-free frames are throttled to one FACT+THUMB `event=scene` item per source per 60 s (4 scene
items for the ~7 min of footage: 73 kB of THUMBs, no FULL), frames with detections but no sighting yet fold, and
`items_deduped` now counts every folded report (592 > 525 because a frame with two tracked objects folds two
DUPLICATEs). The 8 sighting items and 4 contact reports are the same as before (one image item per sighting id:
submarine ×2, coast guard ×2, tanker ×2, cargo ship ×2; 8 CROPs, 58 kB). Sidecar ms/frame was 93 in this run vs 54
before on identical input — single-run noise on a shared VM (the two baseline modes measured ~49 both times); the
per-sighting embedding added in the follow-up is a copy, not extra inference.

Reading it:

- On frames where the tracker holds an object, the edge stored **8 image items for ~250 frames** (one per sighting
  id; `242` frames were folded as `EVENT_DUPLICATE`), each with a CROP form (1.5× key box, ≥96 px, q75, 4–9 kB) and
  `tags{sighting_id, subtype, event}`. 6 of the 8 were key-frame replacements done in place (`event=update`); no
  second FULL was ever queued for the same object because nothing had shipped yet (no shore in this run).
- `hash` ≡ `naive` on real video: consecutive frames never share a SHA-256, so today's dedup never fires (0 folded).
- In the first run the remaining **355 items in `sightings` mode were frames with no tracked object** (open ocean
  before the submarine surfaces, frames where the sunset ship falls under the 0.25 detector threshold), stored with
  hash behaviour as the brief asked. The follow-up `-scene-every` throttle (second table row) folds them: 525 frames
  → **16 items / 1.79 MB**, i.e. 2 % of the frames and 2 % of the bytes of `hash`, with every object still reported
  once with its crop. A scene item has no FULL form, so a shore pull for FULL on a scene finds nothing to send (the
  next scene arrives within `-scene-every`); set `-scene-every 0` to keep one item per object-free frame.
- Sidecar cost is flat at **~50 ms/frame on 4 CPU threads** (≈ 20 fps headroom at 5 fps): YOLO11n-640 FP32 on ORT is
  ~30–35 ms, MobileCLIP-S1 runs only on key-frame crops, the Go side adds JPEG decode + thumb/crop encode. The INT8
  OpenVINO IR (`int8/model.xml`, `--engine openvino`) was not exercised here (openvino not installed in this VM).
- Bytes: FULL frames dominate (54.9 of 56.6 MB); the first rung the scheduler would actually ship first is 66 kB of
  FACTs for 367 items vs 110 kB for 525.

Caveats: single run per mode on one VM, 5 fps replay wall-clock (not CPU-bound); `items_unknown` dropped from 14 to 4
because sighting items carry the key detection instead of the per-frame list. Subtype labels are the zero-shot
classifier's guesses and are not evaluated here (see `edgeml/reports/E.md`).

Reproduce: `edgeml/sidecar/README.md` (integration test) with a scenario JSON whose `sets[].Path` point at the two
`img1/` directories (`gcloud storage cp -r gs://qwiklabs-gcp-02-34a870014566-ghost-seeker/edgeml/eval/ghost_fleet_5fps/<clip> …`),
`-period 200ms`, then `GetStatus` / `GetQueue` / `ListItems` on the edge console.
